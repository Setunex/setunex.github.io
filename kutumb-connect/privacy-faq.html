Privacy & FAQ

Built for data admins can trust with sensitive community details: no server, no accounts, no analytics — only what you import, only on the device you import it to.

Security implementation

What's actually built, not just claimed — and what isn't, yet. Standards referenced: OWASP MASVS (Mobile Application Security Verification Standard) and the OWASP Mobile Top 10.

Protection Status What it does
No server / no accounts Implemented Architecture-level: there is no backend at all, so there's no server to breach, no account database to leak, no API to attack. (MASVS-ARCH)
Screenshot / screen-recording block Implemented Android FLAG_SECURE on the main window — blocks screenshots and screen recording, and redacts the app's content from the recent-apps switcher preview. (MASVS-STORAGE-1)
Excluded from device/cloud backup Implemented android:allowBackup="false" — imported contact data can't be extracted via adb backup or carried off in an automatic cloud backup. (MASVS-STORAGE-2)
Network hardening Implemented Android Network Security Config blocks all cleartext (HTTP) traffic and trusts only system CAs, not user-installed ones — defense-in-depth even though the app makes no network calls of its own. (MASVS-NETWORK-1/2)
Content-Security-Policy Implemented Locks script/object/frame sources to the app itself (script-src 'self', object-src 'none', frame-ancestors 'none') — shrinks the blast radius of any future injection bug. (OWASP ASVS V14, ~Mobile M7)
Minimal data collection Implemented Only a birth year is collected, never a full date of birth — smaller blast radius if data is ever exposed. (data minimization principle)
User-controlled data clearing Implemented Import ▸ "Clear imported data" wipes every community's data from that device immediately, no support request needed.
At-rest encryption of stored contacts Not yet Imported data sits in the OS's app-private storage (not encrypted by the app itself). Real at-rest encryption needs an OS Keystore-backed secure-storage plugin — planned, not shipped. Until then: device-level screen lock + encryption (standard on modern Android) is your actual protection at rest. (MASVS-STORAGE-1)
Login as an access-control boundary By design, not a gate "Login" personalizes the experience (favorites, "you") — it does not restrict who can browse the imported directory. This app is a shared community directory, not a multi-tenant permission system. (MASVS-AUTH \u2014 documented limitation, not a bug)
Root/jailbreak & tamper detection Not yet Not implemented in this pass.

What's deliberately minimized

  • Birth date: only BirthYear is collected — no month or day. The app computes an approximate age from the year alone.
  • No per-person tracking ID: people are identified by their family's FamilyId + name, not a separate ID stitched to one individual.
  • No consent/visibility flags today: everything in the CSV is visible to every logged-in member of that community. Don't put a field in the CSV unless the whole community may see it.

Fields to think twice about

Field Why it's sensitive Guidance
ContactNumber1/2, WhatsApp, EMail Direct contact PII; enables real-world contact or impersonation if leaked. Core to the app's purpose (call/WhatsApp/mail actions, login) — keep, but don't distribute the CSV file itself outside trusted admins.
AddressLine1-3, Pincode Precise home location. Kept by this community's choice. If not needed, use only Area/City/State instead.
LinkedIn, Facebook, Twitter Public profiles, but still directly linkable identity. Optional — only include what the person has already made public.
Mosal, NativeVillage, Kuldevi Lineage/caste-adjacent, culturally significant information. Only include with the family's explicit understanding of why it's collected and who can see it.

Handling the CSV file itself

  • Treat the CSV/Google Sheet as sensitive — restrict edit/view access to trusted admins, same as you would a phone/address book.
  • The Google Sheet builder's Drive file inherits your Drive's sharing settings — check it isn't shared more broadly than intended.
  • Clearing data in-app (Import ▸ "Clear imported data") removes everything from that device; it doesn't affect other admins' copies of the source CSV/Sheet.
This is guidance, not a compliance certification. If your community is subject to specific data-protection law, get that reviewed independently before importing sensitive fields.

FAQ

Can two communities use the same app install without seeing each other's data?

Yes. Each import is scoped to its own CommunityCode; contacts from one community never appear mixed with another's, and importing one doesn't touch the other's storage.

What happens if I accidentally reuse another community's CommunityCode?

The app locks a display name the first time it sees a new CommunityCode. Any later import that would replace an existing community/region's data shows a confirmation dialog with that locked name and the exact row counts before anything is overwritten — nothing happens silently, and a wrong locked name is your cue that the code has already been used by someone else.

How do family members request an update to their details?

Each person's profile shows their family's FamilyId ("quote this + your name to request an update"). They pass that to the admin (WhatsApp, a form, however your community communicates); the admin finds that row in the master Sheet/CSV by FamilyId + name, edits it, and re-imports. There's no in-app self-service editing — this app has no backend to write to.

How does an admin re-import to fix/update existing data?

Edit the same Sheet/CSV and export again with the identical CommunityCode (and RegionCode, if used). That exact combination is what the app matches on to treat it as an upgrade, not a new community.

My community has thousands of members across several states — one CSV?

Split by RegionCode instead: one file per district/state, all sharing the same CommunityCode. Each region can be prepared and re-imported independently without waiting on, or overwriting, the others. See Prepare your CSV.

Do family numbers need to be unique across the whole community?

Only within their own CommunityCode + RegionCode. Each region's admin can number their own families independently — no cross-region coordination needed.

Where is the data actually stored?

On the device, in local app storage. There is no server and no cloud sync built into the app itself — only what you import via CSV.
